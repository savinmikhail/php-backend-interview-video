## Аудит содержания

| Тезис | Оценка | Экранное действие |
|---|---|---|
| integer меньше и естественно упорядочен | корректно | сравнить размер и характер вставки |
| UUID можно создать в приложении до записи | корректно | показать constructor promotion и dispatch до `persist()` |
| UUIDv7 сортируемый/монотонный | уточнить | показать timestamp в старших 48 битах; не обещать строгий порядок внутри одной миллисекунды |
| UUID занимает 12 байт | неверно | исправить: UUID — 128 бит = 16 байт |
| UUID удобен между несколькими БД | корректно | показать независимую генерацию без общей sequence |
| в двух БД не бывает одинаковых UUID | слишком абсолютно | сказать «крайне малая вероятность коллизии»; `UNIQUE` остаётся |
| UUID невозможно подобрать | слишком абсолютно | показать только то, что нельзя вычислить соседний ID как `id + 1` |
| из UUIDv7 видна дата создания записи | уточнить | это время генерации ID, а не гарантированное время `INSERT` |
| `UNSIGNED BIGINT` больше обычного | зависит от СУБД | показать только с подписью MySQL; у PostgreSQL unsigned integer нет |

### Намеренно не показываем

- Точный layout и benchmarks B-tree страниц без данных проекта.
- Все версии UUID и особенности конкретной UUID-библиотеки.
- UUID как автоматически лучший ключ.
- UUID как секрет или средство авторизации.
- Вероятность коллизии в виде длинной формулы.

## Задача визуализации

Сравнить реальную цену ключей, объяснить порядок UUIDv7 и показать практическое
преимущество ID, который существует до записи и не требует общей sequence.

Вертикально две карточки идут друг под другом, аватары — внизу.

## Состояние 2 — размер, вместимость и вставки

```text
┌──────────────────────────────────────────────────────────────┐
│ BIGINT · 8 bytes              UUID · 16 bytes               │
│ до 9.22 × 10¹⁸               128 bit                       │
│ + последовательные вставки    − v4: разные страницы B-tree │
│ − sequence внутри одной БД    + v7: новые ключи рядом       │
│ MySQL UNSIGNED: 1.84 × 10¹⁹                                 │
└──────────────────────────────────────────────────────────────┘
```

Плюсы зелёные, издержки янтарные, нейтральные размеры белые. В 9:16 колонки
перестраиваются вертикально. Исправление считывается из правильного значения
`16 bytes` в колонке UUID и общей плашки `Исправление ответа`; отдельная нижняя
строка его не дублирует.

## Состояние 3 — структура UUIDv7

```text
017F22E2-79B0 | 7 | CC3 | 9 | 8C4-DC0C0C07398F
 timestamp 48   ver  random  variant   random

$id->getDateTime()     22.02.2022 19:22:22 UTC
                       время генерации ID, не INSERT
```

Используется тестовый UUIDv7 из RFC 9562. Подпись сообщает, что строгий порядок
внутри одной миллисекунды зависит от реализации генератора.

## Состояние 4 — ID существует до БД

```php
final class Order
{
    public function __construct(
        private UuidV7 $id = new UuidV7(),
    ) {}
}

$order = new Order();
$bus->dispatch(new OrderCreated($order->id()));
$em->persist($order);
```

Справа крупно: `UuidV7`, `ID уже известен`, `без проверки на null`.

## Состояние 5 — независимые генераторы

```text
Service A / DB A ── UUID A ─┐
                            ├── Event / API · OrderId
Service B / DB B ── UUID B ─┘

+ соседний ID нельзя вычислить как id + 1
```

В 9:16 сервисы складываются сверху вниз. Связь UUID с авторизацией на экран не
выносится: без дополнительного контекста она скорее запутает зрителя.

## Финальный экранный текст

| Элемент | Текст |
|---|---|
| BIGINT | `8 bytes · до 9.22 × 10¹⁸` |
| MySQL | `UNSIGNED BIGINT · до 1.84 × 10¹⁹` |
| UUID | `16 bytes · 128 bit` |
| UUIDv7 | `48-bit timestamp · time-ordered` |
| Несколько БД | `независимая генерация без общей sequence` |

## Анимация

- Плюсы и издержки появляются отдельными строками, без смены смысла цвета.
- Сегменты UUIDv7 сразу окрашены по назначению; затем появляется извлечённое
  время генерации.
- В распределённом состоянии два независимо созданных ID сходятся в общий
  контракт события.
