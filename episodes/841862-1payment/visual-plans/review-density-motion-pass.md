# Итерация по плотности и движению инфографики

Статус: `APPROVED`

Назначение: сохранить контекст следующей проходки по замечаниям
профессионального видеоревью. Документ фиксирует не только предлагаемое
изменение, но и конкретную проблему зрителя, ожидаемую пользу и риск новой
компоновки.

Исходное ревью:
[`06-professional-video-review-2026-09-08.md`](../06-professional-video-review-2026-09-08.md).
Указанные там review-time могли измениться после последующих монтажных вырезов.
Перед реализацией использовать ID сегментов из `video/review-timeline.tsv` и
пересчитывать обе шкалы через `npm run time`.

## Принятый принцип

Замечания нельзя исправлять одним универсальным приёмом.

1. На длинном экране со стабильной структурой направлять внимание двумя-тремя
   смысловыми переключениями.
2. На коротком перегруженном экране сначала уменьшать объём одновременно
   читаемого материала и только затем добавлять движение.
3. В нескольких состояниях одного процесса сохранять пространственную модель:
   элементы не должны без необходимости менять расположение между фазами.
4. Анимация оправдана только тогда, когда следует за смысловым переходом речи.
   Она не используется как декоративное движение.
5. Увеличение контейнеров само по себе не считается повышением читаемости.
   Размер текста остаётся в общей типографической системе; важность задаётся
   ролью текста, иерархией и количеством одновременно видимых деталей.

## Что сохраняем, добавляем и намеренно убираем

- Сохраняем технические выводы существующих слайдов и принятую цветовую
  семантику.
- Добавляем только направленное внимание, постоянные пространственные модели и
  компактные разговорные темы там, где они действительно удерживают контекст.
- Исправления `flush() ≠ clear()` и Cache Aside остаются в видео без служебных
  бейджей.
- AuditLog удаляем из блока onFlush: это необязательный corner case, который
  отвлекает от наблюдаемого поведения flush.
- Полный код Compiler Pass и Cache Aside намеренно не показываем на коротких
  отрезках; сохраняем только обсуждаемые операции.
- Не добавляем инфографику в длинные человеческие фрагменты только ради
  заполнения кадра.
- Не меняем монтажные вырезы по STT и не принимаем решения о длительности
  разговорных частей без оригинального звука.

## Порядок реализации

### Пачка 1 — короткие и критически перегруженные состояния

1. Compiler Pass.
2. onFlush без AuditLog.
3. Identity Map / слои / граница flush.
4. Cache Aside.
5. DateTime — только если проверка в полном таймлайне подтвердит проблему
   переориентации.

### Пачка 2 — длинные экраны и направленное внимание

1. Autowiring.
2. Consumer и Domain/Application через общий разговорный приём.
3. Распределённые UUID.
4. Interface / abstract / trait.

### Контроль без нового дизайна

1. Два длинных разговорных участка.
2. Финальный переход к авторскому аутро и счётчик `/30`.

## Формат ревью реализации

Для статического изменения приложить кадры «было → стало». Для изменения
состояний приложить:

1. исходный кадр;
2. два-три ключевых кадра новой последовательности;
3. короткий MP4-фрагмент в реальном темпе;
4. контрольные кадры 16:9 и 9:16.

Перед изменением тайминга обновить visual plan конкретного вопроса. После
изменения проверить обе временные шкалы, timing lock и четыре boundary-кадра
полной review-композиции.
