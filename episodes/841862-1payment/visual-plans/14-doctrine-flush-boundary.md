## Аудит содержания

| Тезис | Оценка | Экранное действие |
|---|---|---|
| Unit of Work накапливает изменения | корректно | показать одну пачку изменений |
| Повторный поиск одного primary key возвращает тот же managed-объект | корректно в рамках одного EntityManager | показать `SELECT ×1` и identity comparison |
| Репозиторий не должен сам задавать момент `flush()` | корректная архитектурная граница для общей операции | показать, что репозиторий регистрирует изменения, а сценарий завершает Unit of Work |
| Один `flush()` уменьшает число отдельных синхронизаций | корректное практическое правило; число SQL не обязано уменьшиться | показать один boundary и одну transaction |
| `flush()` должен быть строго один на HTTP-request | слишком жёстко | уточнить: один на логическую единицу работы, если нет причины делить её |

Не углубляемся в порядок SQL, batch processing и ручные savepoints. Отдельно
оговариваем: Identity Map не означает, что любой DQL-запрос будет пропущен.

### Намеренно не показываем

- Внутренний commit order Doctrine и количество конкретных SQL-запросов.
- Несколько `flush()` как безусловную ошибку: бывают обоснованные границы.
- Сравнение всех особенностей Doctrine и Eloquent: показываем только отсутствие
  identity map у обычных повторных `find()` в Eloquent.

## Задача визуализации

Показать, как Identity Map связывает работу разных слоёв с одним managed-объектом
и почему репозиторий только регистрирует изменения, а `flush()` остаётся на
уровне сценария, который видит всю логическую единицу работы.

## Анимация и Shorts

- Сначала сравниваются два повторных поиска, затем три сервиса сходятся в одной
  Identity Map и только после этого показывается application boundary.
- Изменения из репозиториев входят в Unit of Work; `flush()` появляется только
  на уровне application service, когда вся операция собрана.
- Хук Shorts: `Репозиторий не видит всю операцию — поэтому не ему делать flush`.
