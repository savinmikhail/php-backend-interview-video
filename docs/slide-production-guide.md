# Гайд по проектированию экранов интервью

## Задача

Экранная графика должна повышать техническую ценность и удержание, а не
дублировать субтитры. Ролик рассчитан прежде всего на опытных разработчиков и
должен сохранять возможность нарезки отдельных вопросов в Shorts.

## Источники для каждого вопроса

Нужны четыре источника:

1. формулировка и краткий ответ из файла вопросов;
2. фрагмент STT-транскрипта с предварительными репликами и таймкодами;
3. решения конкретного выпуска;
4. первичные технические источники для проверки дополнений и исправлений.

Файл вопросов помогает найти тему, а транскрипт — предварительно разметить то,
что прозвучало и где меняется смысл реплики. STT может ошибаться в словах,
говорящих и временных границах, поэтому спорные места синхронизируются по
исходному видео или аудио при реализации.

### Две шкалы времени

В проекте используются две разные шкалы:

- `review-time` — время в `FullInterviewReviewDev` после монтажных вырезов;
- `source-time` — время в исходном интервью и `video/review-timeline.tsv`.

Таймкод пользователя без подписи считается `review-time`. Пересчитывать его
вручную запрещено: из папки `video/` используется
`npm run time -- review-to-source MM:SS`. Обратная проверка выполняется через
`npm run time -- source-to-review HH:MM:SS`, а готовый сегмент печатается сразу
в обеих шкалах командой `npm run time -- segment SLIDE_ID`.

Принятый review-интервал фиксируется в `video/review-timing-locks.tsv` как
проверяемое ожидание. Список вырезов хранится только в
`video/src/editorial-cuts.json`.

### Диаризация и подсветка говорящего

В полной review-композиции активный аватар берётся из сгенерированного
speaker timeline, а не из статического значения конкретного слайда. После
изменения транскрипта, правил сопоставления speaker labels или монтажных
вырезов выполнить из `video/` `npm run speakers:generate`.

Генератор читает source-таймкоды `transcription.txt`, применяет правила и
точечные исправления из `speaker-diarization.config.json`, затем вырезает
удалённые source-интервалы и сохраняет данные в review-шкале. Из-за ошибок STT
автоматическую метку в спорной точке необходимо сверить по оригинальному
звуку; подтверждённое исправление добавляется в config с причиной, а не прямо
в generated JSON. `npm run check` должен отклонять устаревшую карту.

Визуальный план не принимает решений о вырезании, замене или перестановке
исходных реплик. Он покрывает разговор непрерывно, включая участки без учебной
графики. Монтажёр самостоятельно определяет сокращения после просмотра и
прослушивания оригинала.

## Разбор вопроса до дизайна

Для вопроса необходимо зафиксировать:

- начало и конец фрагмента;
- говорящего и смысл каждого отрезка;
- корректные части ответа;
- неточности или опасные упрощения;
- полезные факты, которых в ответе нет;
- материал, который намеренно не показывается;
- пригодность фрагмента для самостоятельного Shorts.

После этого вопрос получает уровень сложности:

| Уровень | Признаки | Экранные состояния | Бюджет |
|---|---|---:|---:|
| S | Короткое определение, достаточно одного примера или вывода | 1 | 10–15 минут |
| M | Нужен код, сравнение либо одно существенное уточнение | 1–2 | 20–40 минут |
| L | Несколько смысловых переходов, ошибка ответа или сложная схема | 2–4 | до 60 минут |

Если вопрос требует больше четырёх состояний или часа работы, его нужно
обсудить отдельно, а не незаметно превращать в отдельный образовательный
ролик.

## Когда нужен экран

Экран оправдан, если выполняет хотя бы одну функцию:

- удерживает в памяти длинный вопрос или различие терминов;
- превращает абстрактное объяснение в код и наблюдаемый результат;
- показывает сравнение, иерархию, поток или связь объектов;
- даёт короткое техническое дополнение;
- исправляет или аккуратно уточняет ответ;
- создаёт самостоятельный понятный фрагмент для Shorts.

Если визуальная польза не сформулирована одним предложением, остаётся базовый
экран с вопросом и аватарами.

## Выбор типа представления

| Содержание | Подходящий паттерн |
|---|---|
| Синтаксис и результат выполнения | Код + результат/ошибка |
| Два похожих понятия | Две смысловые колонки |
| Объекты и ссылки между ними | Схема объектов |
| Последовательность обработки | Flow/sequence |
| 3–4 независимых преимущества | Сетка карточек |
| Существенная ошибка кандидата | Помеченное исправление на слайде |
| Конкретный интерфейс или инструмент | Скриншот с 1–3 аннотациями |

Не нужно выбирать более сложный паттерн только ради движения. Анимация должна
следовать смыслу: появление факта, переход состояния, указание связи.

## Что писать на экране

- Заголовок формулирует вопрос или главный контраст.
- Заголовок карточки — 2–5 слов.
- Пояснение — обычно не больше 8–14 слов.
- Полный ответ абзацем не показывается.
- Реальные сообщения об ошибках указываются полностью, если они читаемы.
- Термины PHP/Symfony и код сохраняют оригинальное написание.
- Надпись должна быть понятна без декоративного бейджа над ней.

Дополнение можно показывать без подписи «Дополнение редакции». Если экран
существенно исправляет или дополняет ответ кандидата, используется конкретная
метка `Уточнение ответа` либо `Исправление`. Досъёмка, переозвучка и
синтетическая замена ответа в визуальных планах не предусматриваются.

## Геометрия и иерархия

- Весь экран строится на одной сетке.
- Если верхние карточки образуют две колонки, код и пояснения под ними
  используют те же колонки и те же края.
- Стрелка или разделитель получают отдельную узкую дорожку либо накладываются
  поверх сетки и не меняют ширину колонок.
- Парные карточки имеют одинаковую высоту и внутренние отступы.
- Внутри экрана сначала читается заголовок, затем основной пример, затем
  вывод. Декор не должен конкурировать с этим порядком.
- Вокруг всей сцены не используется контур. Внутренние рамки показывают
  реальные группы или состояния.

### Цветовые роли

| Роль | Цвет |
|---|---|
| Бренд, readonly, активный акцент | Фиолетовый |
| Структура, тип, обычный объект | Голубой |
| Допустимая операция, успешный результат | Зелёный |
| Ошибка, запрещённая операция | Красный |
| Существенное предупреждение | Жёлтый |

Цвет одной роли нельзя использовать для другой роли на том же экране.
Например, mutable-объект может быть голубым, а допустимая мутация — зелёной.

### Типографика 1080p

PHP-код подсвечивается автоматически через `video/src/PhpCodeBlock.tsx` в
принятой схеме по образцу PhpStorm Dark. Примеры хранятся обычным PHP-текстом:
`PhpCodeBlock` — панель, `PhpTokens` — фрагмент внутри существующего `code`,
`PhpLines` — многострочный блок с отдельными отступами и анимацией строк.
Для `PhpLines` использовать два пробела на уровень вложенности; компонент
переводит их в существующие адаптивные отступы. Смысловые выделения, индексы
old/new и анимацию сохранять отдельно от цветов синтаксиса. SQL, YAML,
результаты и подписи не передавать в PHP-подсветчик.

| Элемент | Ориентир |
|---|---:|
| Главный заголовок | 44–48 px |
| Заголовок карточки | 28–32 px |
| Основной текст | 21–24 px |
| Вторичный текст | 18–20 px минимум |
| Код | 22–26 px |

После полноразмерной проверки кадр обязательно просматривается в масштабе
типичного YouTube-плеера на ноутбуке.

## 16:9 и Shorts

Сначала определяется смысловая структура, затем для неё рисуются два
wireframe. Вертикальный вариант не обязан сохранять расположение широкого:

- две колонки обычно превращаются в последовательность сверху вниз;
- связанные пример, результат и пояснение остаются рядом;
- вопрос и ключевой вывод не попадают под интерфейс Shorts;
- мелкие детали не переносятся ценой уменьшения шрифта;
- фрагмент должен быть понятен зрителю, который не видел предыдущий вопрос.

## Формат предварительного ревью

До реализации используется `templates/question-visual-plan.md`.

- Mermaid показывает только последовательность состояний по времени.
- Положение информации показывают текстовые wireframe 16:9 и 9:16.
- Wireframe содержит названия реальных блоков и короткий экранный текст, а не
  абстрактные `BLOCK 1` и `BLOCK 2`.
- Это не дизайн-макет: цвета, тени и точные пиксели на этом этапе не нужны.

Mermaid не используется для макета экрана: его автоматическая раскладка не
гарантирует положение, размеры и выравнивание блоков.

## Эффективный производственный цикл

1. Разобрать пачку из 5–10 вопросов.
2. Заполнить планы и wireframe без реализации слайдов.
3. Получить одно ревью всей пачки.
4. Собрать принятые состояния на существующих компонентах.
5. Отрендерить по одному контрольному кадру каждого состояния в 16:9 и 9:16.
6. Для каждого изменённого тайминга выполнить
   `npm run render:timing -- SLIDE_ID` и проверить кадры перед началом, на
   начале, перед концом и на конце в полной review-композиции.
7. Исправить только найденные проблемы.
8. Собрать пачку в 10 fps.
9. Сделать 30 fps только для принятого production-варианта.

Новый уникальный компонент создаётся только тогда, когда существующие
паттерны действительно не выражают смысл. Произвольные изображения, SVG и
код допускаются внутри контентных слотов существующей сетки.
